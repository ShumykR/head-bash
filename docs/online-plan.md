# План: онлайн-режим і Telegram

Мета — двоє віддалених гравців грають один матч через інтернет. Та сама гра відкривається:

- **у звичайному браузері** (GitHub Pages, як зараз) — лобі за посиланням/кодом;
- **у Telegram** як Mini App — лобі запускається командою бота в чаті.

Обидва входи — **одна кодова база, одна збірка, один сервер**. Гравець із браузера й гравець із Telegram можуть грати разом.

---

## 1. Ключові рішення

| Питання | Рішення | Чому |
|---|---|---|
| Мережева модель | **Детермінований lockstep із затримкою вводу** | `Game` уже детермінований: фіксований крок 60 Гц, власний seed-ГПВЧ (`game.rand()`), рендер відокремлений. Перевірено: два прогони 7200 кроків із тим самим seed і вводом дають побітово однаковий стан. Вхід — 1 байт на тік (напрямок + дія). Рендер не треба переписувати під знімки стану. |
| Сервер | **Cloudflare Workers + Durable Objects** (TypeScript) | Одна кімната = один Durable Object, що тримає два WebSocket. Безкоштовно, без картки, `wss://` і TLS з коробки на `*.workers.dev`, вузол поруч із гравцями (Варшава/Франкфурт). Telegram-бот — webhook на тому ж Worker. Мова та сама, що в грі, — спільні типи протоколу. |
| Фронтенд | **Лишається на GitHub Pages** | Mini App — це просто HTTPS-адреса; адреса Pages підходить. |
| Telegram | **Адаптер платформи, не форк** | Форк розійдеться з основною грою, а lockstep вимагає побітово однакової симуляції в обох клієнтів. Різниця між платформами — вхід, авторизація, «поділитися», повноекранний режим. |
| Запасний бекенд | Oracle Cloud Always Free (VM, Франкфурт) | Якщо знадобиться серверна перевірка матчу повною симуляцією (у Worker не вистачить CPU). |

### Що свідомо НЕ робимо зараз

- **Rollback (GGPO).** Кращі відчуття, але потребує збереження/відновлення всього світу Planck і стану `Game`. Можна додати пізніше поверх lockstep.
- **Сервер рахує гру й розсилає стан.** Рендер читає живі об'єкти `Game` — довелося б переробити весь `src/render`.
- **Рейтинг, таблиці лідерів, історія матчів.** Після запуску базового режиму.
- **Серверна перевірка результату симуляцією.** Сервер вірить звітам клієнтів, але звіряє хеші обох; розбіжність = матч не зараховано.

## 3. Протокол (`src/net/protocol.ts`)

JSON на етапі лобі, компактні повідомлення під час матчу. Кожне повідомлення має `t` (тип).

**Клієнт → сервер**

| t | Поля | Коли |
|---|---|---|
| `hello` | `build` (sha), `proto`, `name`, `auth?` (Telegram initData) | одразу після підключення |
| `pick` | `car` | вибір авто в лобі |
| `config` | `map`, `target`, `roundTime`, `randomCars` | лише хост |
| `ready` | — | готовий до старту |
| `in` | `k` (тік), `b` (біти: ліво/право/дія) | лише коли ввід змінився + раз на 0.5 с «без змін» |
| `hash` | `k`, `h` | кожні 60 тіків |
| `result` | `winner`, `scores` | кінець матчу |
| `ping` | `ts` | раз на 2 с |

**Сервер → клієнт**

| t | Поля | Коли |
|---|---|---|
| `welcome` | `slot` (0/1), `room`, `peer?` | після `hello` |
| `lobby` | стан обох гравців, конфіг | при кожній зміні |
| `start` | `seed`, `cars`, `config`, `delay` (тіків) | обидва `ready` |
| `in` | `p`, `k`, `b` | пересилання вводу суперника |
| `desync` | `k` | хеші за тік `k` не збіглися |
| `peerLeft` / `peerBack` | — | обрив / повернення суперника |
| `end` | `winner`, `reason` (`score` / `forfeit` / `desync`) | кінець матчу |
| `pong` | `ts` | відповідь на ping |
| `reject` | `reason` (`version`, `full`, `notFound`) | відмова |

Сервер не пускає в кімнату клієнти з різними `build` → клієнт пропонує перезавантажитися (важливо через Service Worker і кеш WebView у Telegram).

## 4. Мережевий код (lockstep)

1. Після `start` обидва клієнти створюють `Game` з однаковим `seed`, авто й конфігом.
2. Ввід, зібраний на кадрі, призначається тіку `current + delay` (`delay` ≈ RTT/2 / 16.7 мс + 2, у межах 3–8). Він одразу йде на сервер і в локальний буфер.
3. Тік `k` виконується (`game.step()`) лише коли відомий ввід **обох** гравців на `k`. Бракує вводу суперника → чекаємо (рендер продовжує малювати, гра «підвисає»). Повідомлення шлються лише при зміні вводу, тож «немає нових даних до тіку N» означає «ввід той самий».
4. Темп: кроки викликаються з `main.ts` напряму, без `FixedStepper` на реальному часі; slow-mo лишається суто темпом відтворення (обидва клієнти рахують його з однакового стану — на результат не впливає).
5. Кожні 60 тіків — хеш стану на сервер. Розбіжність → `desync` → матч зупиняється й не зараховується (на першому етапі; відновлення стану — пізніше).
6. Обрив: суперник зник → пауза з таймером 15 с → `peerBack` (кімната переслала пропущений ввід) або технічна поразка.

### Що змінити в наявному коді

| Файл | Зміна |
|---|---|
| `src/game/game.ts:1658` | `Math.random()` → `this.rand()` (напрямок вильоту водія) |
| `src/game/ragdoll.ts:21` | `Math.random()` → ГПВЧ гри (обертання голови ragdoll — тіло у світі, впливає на фізику) |
| `src/main.ts` | режим `online`: ввід локального гравця → `NetMatch`; тіки з `lockstep`; без паузи (кнопка «II» → «Здатися»); `visibilitychange` не ставить на паузу, а лише попереджає |
| `src/input/input.ts` | своя розкладка завжди керує своїм слотом (гість — P2 клавішами P1); на телефоні `solo`-розкладка |
| `src/ui/menu.ts` | пункт «Онлайн» → `src/ui/lobby.ts` |
| `src/ui/pwa.ts` | у Telegram не реєструвати Service Worker і не показувати встановлення |
| камера/HUD | гість бачить себе так само, як P1 (за потреби — дзеркальні підписи рахунку «Ти / Суперник») |

## 5. Етапи

Оцінки — робочі дні одного розробника.

### Етап 0. Детермінізм між рушіями — 2–4 дні · **блокує все інше**

Ризик: iOS (WebKit/JSC) і Android/десктоп (Chromium/V8) можуть по-різному округлювати `Math.sin/cos/tan/atan2/exp/log/pow`. Planck ними користується → гра розійдеться за кілька секунд.

- [ ] Скрипт `scripts/detcheck.ts`: фіксований seed + записаний ввід → хеш стану кожні 60 тіків. Запуск у Node.
- [ ] Та сама перевірка в браузерах через Playwright: Chromium (є) і WebKit (`npx playwright install webkit`), порівняння хешів.
- [ ] Прибрати `Math.random` із симуляції (два місця вище) + тест, що симуляція не викликає `Math.random`.
- [ ] Якщо хеші розходяться — `src/net/detmath.ts` (порт fdlibm) і підміна `Math.*` до завантаження Planck; повторна перевірка.
- [ ] Хеш стану `src/net/hash.ts` + тест.

**Готово, коли:** 10 хв матчу з випадковими авто й аренами дають однакові хеші в Node, Chromium і WebKit.

### Етап 1. Сервер-каркас — 3–4 дні

- [ ] `server/` з Wrangler, Worker-маршрутизатор, Durable Object `Room`.
- [ ] Лобі: створення кімнати (код із 4–5 символів без схожих літер), приєднання, `pick`/`config`/`ready`, `start` із seed.
- [ ] Пересилання `in`, звірка `hash`, `ping/pong`.
- [ ] Перевірка `build`/`proto`, ліміт 2 гравці, таймаут порожньої кімнати.
- [ ] Обрив і повернення (вікно 15 с), технічна поразка.
- [ ] WebSocket Hibernation API (кімната не тратить ліміт часу, поки чекає в лобі).
- [ ] Тести кімнати локально (miniflare).

**Готово, коли:** два тестові клієнти в тестах проходять лобі → матч → результат, обрив і повернення.

### Етап 2. Мережевий клієнт — 4–6 днів

- [ ] `src/net/client.ts`: підключення, перепідключення з тим самим місцем, вимір RTT.
- [ ] `src/net/lockstep.ts`: буфер вводу, затримка, виконання тіків, хеші.
- [ ] Інтеграція в `main.ts` (режим `online`), `input.ts` (свій слот).
- [ ] Індикатор пінгу й «очікування суперника» в HUD.
- [ ] Емуляція поганої мережі в тестах (затримка, джиттер, втрати → перепідключення).

**Готово, коли:** дві вкладки на одному ПК грають повний матч через локальний `wrangler dev`, хеші збігаються.

### Етап 3. Інтерфейс онлайн-лобі — 3–4 дні

- [ ] Меню: «Онлайн» → «Створити гру» / «Увійти за кодом».
- [ ] Екран лобі: код і кнопка «Поділитися», обидва гравці, їхні авто, налаштування хоста, «Готовий».
- [ ] Вибір авто — наявний гараж (`src/ui/garage.ts`) у режимі лобі.
- [ ] Відкриття за посиланням `?room=CODE` одразу веде в лобі.
- [ ] Екрани помилок: стара версія, кімната повна/не існує, суперник вийшов, розсинхрон.
- [ ] Кінець матчу: «Реванш» (та сама кімната) / «В меню».

### Етап 4. Деплой — 1–2 дні

- [ ] Акаунт Cloudflare, `CLOUDFLARE_API_TOKEN` у секретах GitHub.
- [ ] Job `deploy-server` у `.github/workflows/deploy.yml`: `wrangler deploy` з `main` (лише коли змінено `server/` або `src/net/protocol.ts`).
- [ ] Адреса сервера в клієнті через `import.meta.env` (`VITE_SERVER_URL`), для гілок — локальна або staging.
- [ ] Порядок деплою: спершу сервер (сумісний із попереднім `proto`), потім Pages.

**Готово, коли:** гра на Pages грає онлайн через `*.workers.dev`.

### Етап 5. Telegram — 3–5 днів

- [ ] BotFather: бот, `/newapp` з адресою Pages, коротка назва Mini App.
- [ ] `src/platform/telegram.ts`: `telegram-web-app.js`, `initData`, `start_param` → код кімнати, `requestFullscreen`, `lockOrientation`, `disableVerticalSwipes`, кнопка «Назад», haptics при ударі/очку, safe-area.
- [ ] `server/src/tgauth.ts`: перевірка підпису `initData` (HMAC-SHA256 з ключем від `WebAppData` + токен бота), ім'я й id гравця з Telegram.
- [ ] `server/src/bot.ts`: `/duel` у групі → кімната + повідомлення з кнопкою-посиланням `t.me/<bot>/<app>?startapp=<код>` (у групах кнопки `web_app` заборонені); оновлення повідомлення, коли хтось приєднався; рахунок після матчу.
- [ ] Inline-режим (`@bot` у будь-якому чаті → «Кинути виклик») — за бажанням.
- [ ] Секрети: `TG_BOT_TOKEN`, `TG_WEBHOOK_SECRET` у Wrangler secrets.

**Готово, коли:** у тестовій групі `/duel` → двоє натискають кнопку → матч → бот пише результат.

### Етап 6. Тести на пристроях і полірування — 2–3 дні

- [ ] iPhone (Safari + Telegram) ↔ Android (Chrome + Telegram) ↔ десктоп: повні матчі, хеші.
- [ ] Мобільна мережа (4G), перемикання Wi-Fi ↔ 4G посеред матчу.
- [ ] Згортання застосунку / дзвінок посеред матчу.
- [ ] Підбір затримки вводу за відчуттями.
- [ ] Оновити README (розділ «Онлайн»).

## 6. Ризики

| Ризик | Ймовірність | Що робимо |
|---|---|---|
| Розсинхрон WebKit ↔ V8 через `Math.*` | середня | Етап 0 до будь-чого іншого; детермінована математика; хеші в кожному матчі |
| Прихована недетермінованість у грі (порядок обходу, стан поза `Game`, кеш між матчами) | середня | Хеш стану з детальним розкладом (по тілах) для діагностики; детчек у CI |
| Затримка вводу відчутна на 4G | середня | Адаптивна затримка; пізніше — rollback |
| Ліміти безкоштовного Cloudflare (100k запитів/добу, вхідне WS-повідомлення = 1/20 запиту) | низька на старті | Ввід лише при зміні → ~500+ матчів/добу; при рості — Workers Paid $5/міс |
| Різні версії клієнтів (кеш SW, WebView) | висока без захисту | `build` у `hello`, відмова й перезавантаження |
| Зміни в грі ламають детермінізм непомітно | середня | Детчек-тест у `npm test` на записаному матчі |

## 8. Відкриті питання

- Хто обирає арену в онлайні: хост, випадково чи кожен гравець «банить» по одній?
- Чи потрібен публічний пошук суперника (черга «грати з будь-ким»), чи лише за запрошенням?
- Що показувати в чаті після матчу: лише рахунок чи ще й авто/арену?
